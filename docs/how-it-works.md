# Как устроен проект (шпаргалка к экзамену)

Простое объяснение: что где лежит, как работает и почему сделано именно
так. Перечитай перед экзаменом. Если тебя спросят «почему так?», ответы
здесь.

## 1. Большая картина: проект как ресторан

```
Postman / React  →  Express (сервер)  →  PostgreSQL (база)
   клиент            официант + кухня      склад (в Docker)
```

- **Клиент** (сейчас Postman, потом React) делает заказ: «дай список
  пользователей».
- **Сервер** принимает заказ, проверяет, имеет ли клиент на него право, и
  готовит ответ.
- **База** хранит все данные. Клиент **никогда** не ходит в неё напрямую,
  только через сервер. Поэтому сервер решает, кому что можно.

## 2. Что мы используем и зачем

| Технология        | Что это                           | Где у нас                 | Зачем                                              |
| ----------------- | --------------------------------- | ------------------------- | -------------------------------------------------- |
| **Node.js 24**    | запускает JavaScript вне браузера | —                         | на нём работает сервер                             |
| **Express 5**     | фреймворк для сервера             | `server/src/`             | принимает запросы и отдаёт ответы                  |

| **pg**            | библиотека «Node ↔ Postgres»      | `server/src/db.ts`        | отправляет наш SQL в базу                          |
| **zod**           | проверка входящих данных          | `server/src/schemas/`     | «телефон точно в формате +998…?»                   |

| **jsonwebtoken**  | создаёт и проверяет токены (JWT)  | `server/src/utils/jwt.ts` | «пропуск» после входа                              |
| **cookie-parser** | читает cookie из запроса          | `server/src/app.ts`       | достаёт токен                                      |
| **Docker**        | запускает программы в контейнерах | `docker-compose.yml`      | база без установки, одинаковая на любом компьютере |
| **Postman**       | клиент для проверки API           | `postman/`                | тестируем API без фронтенда                        |
| **Prettier**      | автоформатирование кода           | корень проекта            | весь код в одном стиле                             |
| **React + Vite**  | фронтенд (после экзамена)         | `client/`                 | интерфейс админки                                  |

**Почему без ORM (Prisma, Sequelize)?** Мы пишем SQL руками через `pg`. Так
ты видишь каждый запрос, учишь настоящий SQL, а схема базы лежит в
`docs/database/*.sql`.

## 3. Как запрос проходит через сервер

Пример: `POST /api/v1/auth/login`.

| Шаг | Файл                                 | Роль в ресторане  | Что делает                                         |
| --- | ------------------------------------ | ----------------- | -------------------------------------------------- |
| 1   | `src/index.ts`                       | открывает двери   | запускает сервер на порту 4000                     |
| 2   | `src/app.ts`                         | администратор     | подключает `express.json()`, cookie и все маршруты |
| 3   | `src/routes/auth.routes.ts`          | меню              | связывает адрес с функцией: `/login` → `login`     |
| 4   | `src/schemas/auth.schema.ts`         | охранник на входе | zod проверяет формат телефона и пароля             |
| 5   | `src/controllers/auth.controller.ts` | официант          | принимает запрос и решает, что ответить            |
| 6   | `src/services/user.service.ts`       | повар             | SQL: `SELECT ... WHERE phone = $1`                 |
| 7   | `src/db.ts`                          | дверь на склад    | подключение к базе (Pool)                          |

**Правило:** SQL живёт только в `services`, логика запроса только в
`controllers`. Это называется **разделение ответственности** (separation of
concerns): каждый файл делает одно дело, поэтому код легко читать и менять.

**Почему `$1`, а не подставить телефон в строку?** Это параметризованный
запрос. База получает данные отдельно от SQL, поэтому SQL-инъекция
невозможна.

## 4. Логин и токен

**Проблема:** HTTP ничего не помнит. Для сервера каждый запрос приходит от
незнакомца. Ты вошёл, а следующий запрос сервер уже не узнаёт.

**Решение: токен.** Это как браслет в аквапарке: на входе показал билет,
тебе надели браслет, и дальше на каждой горке ты показываешь только
браслет.

1. Клиент отправляет `{ phone, password }`.
2. **zod** проверяет формат. Если формат неправильный → **400** с
   `details`.
3. Сервер ищет пользователя по телефону.
4. **bcrypt** сравнивает пароль с хешем. В базе лежит не пароль, а
   «отпечаток» `$2b$12$...`. Даже если базу украдут, паролей там нет.
5. Если пароль неверный → **401** «Invalid phone or password». Это
   **одно и то же сообщение** для неизвестного телефона и неверного
   пароля, иначе хакер мог бы узнавать, чей номер зарегистрирован.
6. Если аккаунт выключен (`status = false`) → **403**.
7. Если всё верно, сервер создаёт **JWT** с `{ sub: id, role }` и
   подписывает его секретом `JWT_SECRET`. Подделать токен нельзя: подпись
   не сойдётся. Он живёт 1 день.
8. Токен кладётся в **httpOnly-cookie**. Браузер сам прикладывает её к
   каждому запросу, а JavaScript на странице прочитать её **не может**.
   Поэтому вредный скрипт не украдёт токен (защита от XSS).
9. `GET /me` («кто я?»): `requireAuth` проверяет браслет, а потом
   пользователь загружается из базы заново. Поэтому выключенный аккаунт
   теряет доступ сразу.
10. `POST /logout` удаляет cookie (снимает браслет).

**Честное ограничение (могут спросить):** JWT нельзя «отозвать». Если
токен скопировали, он работает до конца срока (1 день). Настоящий отзыв
требует списка токенов на сервере, и это сделаем позже, если понадобится.

Где: `src/controllers/auth.controller.ts`, `src/utils/jwt.ts`,
`src/middleware/auth.middleware.ts`.

## 5. Error handling и лог ошибок

**Error handling** — это страховочная сетка: код, который ловит **все**
ошибки и превращает их в понятный JSON.

- **Без него** Express показывает HTML-страницу со внутренностями сервера,
  а при упавшей базе всё может просто вылететь.
- **С ним** 400 / 401 / 403 / 404 / 500 всегда приходят как JSON
  `{ "error": "..." }`. Клиенту говорим только «Internal server error», а
  настоящую причину видишь ты.

Где: `src/middleware/error.middleware.ts`. `notFound` отвечает 404 на
неизвестные адреса, `errorHandler` ловит всё остальное. Оба подключены
**последними** в `app.ts`, потому что ловят то, что не поймали раньше.

**Лог-файл.** Каждая ошибка 500 и каждый обрыв связи с базой
записываются:

- в терминал (как раньше);
- в файл **`server/logs/error.log`**: дата и время по Ташкенту, где
  случилось (`500 POST /api/v1/auth/login`) и полный стек ошибки. Старые
  записи остаются, новые дописываются в конец.

Код: `src/utils/logger.ts` (функция `logError`). Папка `logs/` в
`.gitignore`: логи не попадают в git. **Тела запросов в лог не пишем**:
там могут быть пароли.

Позже, на настоящем сервере, файл будет расти бесконечно. Тогда добавим
ротацию (каждый день новый файл) или библиотеку вроде
[pino](https://getpino.io/).

## 6. TypeScript за минуту

Это JavaScript с подписями типов. Пишешь `phone: string`, и редактор
знает, что там строка. Опечатка `user.emial` подчёркивается сразу, ещё до
запуска.

- `npm run dev` запускает код **без проверки типов** (быстро).
- `npm run typecheck` **проверяет типы**. Запускай перед каждым коммитом.
- `import type { ... }` нужен для импорта, который является только типом.
- Настройки: `server/tsconfig.json`.

## 7. Docker

### Что это

Docker запускает программы в **контейнерах**. Контейнер — как коробка для
переезда: внутри программа и всё, что ей нужно (нужная версия, библиотеки,
настройки). Коробка одинаково открывается на любом компьютере. Поэтому
пропадает вечная проблема «у меня работает, а у тебя нет».

| Слово             | Простыми словами                                | У нас                              |
| ----------------- | ----------------------------------------------- | ---------------------------------- |
| **Образ** (image) | рецепт, только для чтения                       | `postgres:18`                      |
| **Контейнер**     | запущенная программа, приготовленная по рецепту | `it-live-lms-db`                   |
| **Volume**        | сейф для данных: живёт отдельно от контейнера   | `db-data` (наша база)              |
| **Порт**          | дверь из контейнера наружу                      | `5433` (снаружи) → `5432` (внутри) |
| **Compose**       | один файл описывает все контейнеры проекта      | `docker-compose.yml`               |
| **Docker Hub**    | «магазин» готовых образов                       | оттуда скачан `postgres:18`        |

### Контейнер против виртуальной машины

Виртуальная машина — отдельный дом со своим фундаментом (своя операционная
система целиком): тяжёлая, долго запускается. Контейнер — квартира в общем
доме: фундамент (ядро системы) общий, поэтому контейнер лёгкий и стартует
за секунды.

### Docker на Windows

Docker придумали для Linux: контейнеры используют **ядро Linux**. У Windows
другое ядро, поэтому **Docker Desktop** на Windows тихо запускает маленький
Linux через **WSL 2**. Именно поэтому мы ставили WSL. То есть Docker на
Windows работает, но внутри всё равно Linux. (Бывают и Windows-контейнеры
для программ только под Windows, но нам они не нужны.)

На настоящем сервере (VPS с Linux) Docker работает напрямую, без Docker
Desktop и без WSL.

### Что делает наш `docker-compose.yml`

- берёт образ `postgres:18`;
- называет контейнер `it-live-lms-db`;
- берёт пароль и имя базы из корневого `.env`;
- открывает порт **5433** на твоём компьютере (5432 занят старым Postgres,
  установленным в Windows);
- хранит данные в volume `db-data`, поэтому они переживают перезапуск;
- при **самом первом** запуске (пустой volume) сам выполняет SQL-файлы из
  `docs/database/`, то есть создаёт все 18 таблиц;
- `restart: unless-stopped`: база сама поднимается вместе с Docker
  Desktop.

### Команды (из корня проекта)

| Команда                     | Что делает                                            |
| --------------------------- | ----------------------------------------------------- |
| `docker compose up -d`      | создать и запустить (если ещё нет)                    |
| `docker compose ps`         | статус: запущена ли база                              |
| `docker compose stop`       | остановить (данные сохраняются)                       |
| `docker compose start`      | запустить снова                                       |
| `docker compose logs db`    | логи базы                                             |
| `docker compose down`       | удалить контейнер (данные в volume остаются)          |
| ⚠️ `docker compose down -v` | удалить контейнер **и все данные**. Только осознанно! |

**Главное правило:** Docker Desktop должен быть **запущен**, иначе базы
нет и сервер отвечает 500 / health 503.

### Интерфейс Docker Desktop

Слева меню, по центру список. Названия пунктов зависят от версии, главные
такие:

- **Containers**: запущенные и остановленные контейнеры. Здесь
  `it-live-lms` → `it-live-lms-db`: зелёная точка — работает, кнопки ▶
  (start), ⏹ (stop), 🗑 (delete). Клик по контейнеру открывает вкладки
  **Logs** (то же, что `docker compose logs`), **Inspect** (настройки),
  **Exec** (терминал внутри контейнера), **Stats** (память и процессор).
- **Images**: скачанные образы (`postgres:18`, около 650 МБ).
- **Volumes**: сейфы с данными. Здесь `it-live-lms_db-data`, в нём наша
  база. Удалишь его — удалишь данные.
- **Builds**: сборки собственных образов (понадобится при деплое).
- **Docker Hub / Scout / Extensions / Models / Ask Gordon**: магазин
  образов, проверка уязвимостей, плагины, AI-модели, AI-помощник. Нам пока
  не нужны.
- Внизу: статус **Engine running** (Docker работает), расход памяти и
  процессора. Шестерёнка вверху справа — настройки.

### Что ещё можно делать с Docker

- **Запускать что угодно без установки:** Redis (кеш), MinIO (хранилище
  файлов как Amazon S3, пригодится для материалов курсов), Nginx,
  pgAdmin. Одна строчка в `docker-compose.yml`, и сервис готов. Не нужен —
  удалил, в системе ничего не осталось.
- **Держать разные версии рядом:** Postgres 16 для одного проекта и 18 для
  другого, без конфликтов.
- **Упаковать наш собственный сервер и фронтенд** в образы (через
  `Dockerfile`) и запустить их на VPS одной командой. Это шаг «первый
  деплой».
- **Тесты в CI** (GitHub Actions): тесты запускаются в таком же контейнере,
  как у тебя.
- **Новый разработчик** делает `git clone` + `docker compose up` и через
  минуту у него та же база, что у тебя.

## 8. Как смотреть базу в pgAdmin

У тебя **два** Postgres: порт **5432** — установленный в Windows (не наш),
порт **5433** — наш, в Docker.

1. Открой **pgAdmin 4** из меню «Пуск».
2. Правой кнопкой по **Servers** → **Register → Server…**
3. **General → Name:** `IT Live LMS (Docker)`.
4. **Connection:** Host `localhost`, Port **`5433`**, Maintenance database
   `it_live_lms`, Username `lms`, Password из корневого `.env`
   (`POSTGRES_PASSWORD`). **Save**.

Таблицы: **IT Live LMS (Docker) → Databases → it_live_lms → Schemas →
public → Tables**. Данные: правой кнопкой по таблице → **View/Edit Data →
All Rows**. Свой SQL: выдели базу → **Tools → Query Tool**.

Без pgAdmin, из терминала:

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT id, phone, full_name FROM users;"'
```

## 9. Postman

- **Коллекция** «IT Live LMS API»: папки Health, Auth, Errors. Каждый
  запрос с автотестами (вкладка **Scripts → Post-response**).
- **Environment** «IT Live LMS (local)»: `baseUrl`, `adminPhone`,
  `adminPassword`. В запросах они пишутся как `{{adminPhone}}`. Значения
  вводишь сам, в git они не попадают.
- **Run** на коллекции запускает все запросы с тестами по порядку.
- Postman хранит cookie как браузер, поэтому после **Login** запрос **Me**
  работает сам.
- **Главная копия** — файлы в `postman/` в репозитории. Копия в облаке
  Postman (workspace menTalabaman) обновляется после каждого изменения
  файла.

## 10. Как запустить проект (или показать другому)

```bash
# 1. База (Docker Desktop должен быть открыт)
docker compose up -d

# 2. Сервер
cd server
npm install
npm run db:seed   # роли и первый админ (повторный запуск безопасен)
npm run dev       # http://localhost:4000

# 3. Postman: Import → оба файла из postman/ → заполнить environment → Run
```
