# Как устроен проект (шпаргалка к экзамену)

Простое объяснение: что где лежит, как работает и почему сделано именно
так. Перечитай перед экзаменом. Если тебя спросят «почему так?», ответы
здесь.

## 1. Большая картина: проект как ресторан

```
Postman / React  →  Express (сервер)  →  PostgreSQL (база)
   клиент            официант + кухня      склад (в Docker)
```

- **Клиент** (сейчас Postman, потом React) делает заказ: «дай список
  пользователей».
- **Сервер** принимает заказ, проверяет, имеет ли клиент на него право, и
  готовит ответ.
- **База** хранит все данные. Клиент **никогда** не ходит в неё напрямую,
  только через сервер. Поэтому сервер решает, кому что можно.

**Почему без ORM (Prisma, Sequelize)?** Мы пишем SQL руками через `pg`. Так
ты видишь каждый запрос, учишь настоящий SQL, а схема базы лежит в
`docs/database/*.sql`.

## 3. Как запрос проходит через сервер

Пример: `POST /api/v1/auth/login`.

| Шаг | Файл                                 | Роль в ресторане  | Что делает                                         |
| --- | ------------------------------------ | ----------------- | -------------------------------------------------- |
| 1   | `src/index.ts`                       | открывает двери   | запускает сервер на порту 4000                     |
| 2   | `src/app.ts`                         | администратор     | подключает `express.json()`, cookie и все маршруты |
| 3   | `src/routes/auth.routes.ts`          | меню              | связывает адрес с функцией: `/login` → `login`     |
| 4   | `src/schemas/auth.schema.ts`         | охранник на входе | zod проверяет формат телефона и пароля             |
| 5   | `src/controllers/auth.controller.ts` | официант          | принимает запрос и решает, что ответить            |
| 6   | `src/services/user.service.ts`       | повар             | SQL: `SELECT ... WHERE phone = $1`                 |
| 7   | `src/db.ts`                          | дверь на склад    | подключение к базе (Pool)                          |

**Правило:** SQL живёт только в `services`, логика запроса только в
`controllers`. Это называется **разделение ответственности** (separation of
concerns): каждый файл делает одно дело, поэтому код легко читать и менять.

**Почему `$1`, а не подставить телефон в строку?** Это параметризованный
запрос. База получает данные отдельно от SQL, поэтому SQL-инъекция
невозможна.

## 4. Логин и токен

**Проблема:** HTTP ничего не помнит. Для сервера каждый запрос приходит от
незнакомца. Ты вошёл, а следующий запрос сервер уже не узнаёт.

**Решение: токен.** Это как браслет в аквапарке: на входе показал билет,
тебе надели браслет, и дальше на каждой горке ты показываешь только
браслет.

1. Клиент отправляет `{ phone, password }`.
2. **zod** проверяет формат. Если формат неправильный → **400** с
   `details`.
3. Сервер ищет пользователя по телефону.
4. **bcrypt** сравнивает пароль с хешем. В базе лежит не пароль, а
   «отпечаток» `$2b$12$...`. Даже если базу украдут, паролей там нет.
5. Если пароль неверный → **401** «Invalid phone or password». Это
   **одно и то же сообщение** для неизвестного телефона и неверного
   пароля, иначе хакер мог бы узнавать, чей номер зарегистрирован.
6. Если аккаунт выключен (`status = false`) → **403**.
7. Если всё верно, сервер создаёт **JWT** с `{ sub: id, role }` и
   подписывает его секретом `JWT_SECRET`. Подделать токен нельзя: подпись
   не сойдётся. Он живёт 1 день.
8. Токен кладётся в **httpOnly-cookie**. Браузер сам прикладывает её к
   каждому запросу, а JavaScript на странице прочитать её **не может**.
   Поэтому вредный скрипт не украдёт токен (защита от XSS).
9. `GET /me` («кто я?»): `requireAuth` проверяет браслет, а потом
   пользователь загружается из базы заново. Поэтому выключенный аккаунт
   теряет доступ сразу.
10. `POST /logout` удаляет cookie (снимает браслет).

**Честное ограничение (могут спросить):** JWT нельзя «отозвать». Если
токен скопировали, он работает до конца срока (1 день). Настоящий отзыв
требует списка токенов на сервере, и это сделаем позже, если понадобится.

Где: `src/controllers/auth.controller.ts`, `src/utils/jwt.ts`,
`src/middleware/auth.middleware.ts`.

## 5. Error handling и лог ошибок

**Error handling** — это страховочная сетка: код, который ловит **все**
ошибки и превращает их в понятный JSON.

- **Без него** Express показывает HTML-страницу со внутренностями сервера,
  а при упавшей базе всё может просто вылететь.
- **С ним** 400 / 401 / 403 / 404 / 500 всегда приходят как JSON
  `{ "error": "..." }`. Клиенту говорим только «Internal server error», а
  настоящую причину видишь ты.

Где: `src/middleware/error.middleware.ts`. `notFound` отвечает 404 на
неизвестные адреса, `errorHandler` ловит всё остальное. Оба подключены
**последними** в `app.ts`, потому что ловят то, что не поймали раньше.

**Лог-файл.** Каждая ошибка 500 и каждый обрыв связи с базой
записываются:

- в терминал (как раньше);
- в файл **`server/logs/error.log`**: дата и время по Ташкенту, где
  случилось (`500 POST /api/v1/auth/login`) и полный стек ошибки. Старые
  записи остаются, новые дописываются в конец.

Код: `src/utils/logger.ts` (функция `logError`). Папка `logs/` в
`.gitignore`: логи не попадают в git. **Тела запросов в лог не пишем**:
там могут быть пароли.

Позже, на настоящем сервере, файл будет расти бесконечно. Тогда добавим
ротацию (каждый день новый файл) или библиотеку вроде
[pino](https://getpino.io/).

## 5.1 Админ-API: категории, уровни, курсы (CRUD)

**CRUD** = Create, Read, Update, Delete: четыре действия над любой
таблицей. В REST каждое действие — свой HTTP-метод:

| Действие | Запрос                           | Ответ                    |
| -------- | -------------------------------- | ------------------------ |
| список   | `GET /api/v1/admin/courses`      | 200 `{ courses, total }` |
| один     | `GET /api/v1/admin/courses/7`    | 200 или 404              |
| создать  | `POST /api/v1/admin/courses`     | **201** Created          |
| изменить | `PATCH /api/v1/admin/courses/7`  | 200 или 404              |
| удалить  | `DELETE /api/v1/admin/courses/7` | **204** No Content       |

То же для `/categories` и `/levels`. Коды:
[MDN, HTTP status](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status).

**Защита.** В `routes/admin.routes.ts` одна строка
`router.use(requireAuth, requireRole("admin"))` закрывает все маршруты
админки. Без cookie — 401 («кто ты?»), не админ — 403 («знаю тебя, но
нельзя»).

**Файлы модуля** — те же 4 слоя, что у логина: `schemas/` (zod) →
`controllers/` → `services/` (SQL) → `routes/`. Общие помощники лежат в
`utils/` (`http.ts`, `pg-errors.ts`, `sql.ts`, `slug.ts`) и
`schemas/common.schema.ts`.

**Решения, которые стоит уметь объяснить:**

1. **PATCH, а не PUT.** PATCH меняет только присланные поля.
   `utils/sql.ts → buildSet` собирает `SET title = $1, status = $2` из
   того, что пришло. Имена колонок попадают в текст SQL, но они из
   проверенной zod-схемы (zod выбрасывает незнакомые ключи), а значения
   всё равно идут через `$1`. Поэтому SQL-инъекции нет.
2. **Нет `.default()` в схеме создания.** Схема PATCH = та же схема с
   `.partial()`. С `default(true)` PATCH без `status` включал бы курс
   обратно. Значения по умолчанию ставит база.
3. **Ошибки базы → понятные ответы.** У PostgreSQL каждая ошибка имеет
   код ([список](https://www.postgresql.org/docs/current/errcodes-appendix.html)):
   - `23505` повтор уникального значения (тот же slug) → **409 Conflict**;
   - `23503` курс с несуществующей `category_id` → **400** для этого поля;
   - `23001` удаление категории, у которой есть курсы (`ON DELETE
RESTRICT`) → **409**. Этот код нашли тесты Postman: сначала ловили
     только 23503, и сервер отвечал 500.
4. **Удалить или выключить.** Курс с оплатами удалить нельзя: деньги —
   это история, база не даст (RESTRICT). Для этого есть `status: false`.
5. **Необязательные фильтры** одним SQL: `($2::int IS NULL OR
c.category_id = $2)`. Фильтра нет → передаём `null` → условие
   пропускается.
6. **Пагинация:** `LIMIT 10 OFFSET 20` = 3-я страница. Второй запрос
   `COUNT(*)` с тем же WHERE даёт `total`. Оба запускаются одновременно
   через [`Promise.all`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/all).
7. **Ловушка `z.coerce.boolean()`:** `Boolean("false")` = `true`
   (непустая строка). Поэтому `?status=` проверяем как
   `z.enum(["true", "false"])`.
8. **Типы из pg:** `COUNT(*)` приходит строкой → пишем `COUNT(*)::int`.
   `price` (NUMERIC) оставляем строкой `"1200000.00"`, чтобы не терять
   точность денег.
9. **slug** (`frontend-react`) делается из названия, если админ его не
   прислал (`utils/slug.ts`).

## 5.2 Пользователи (Foydalanuvchilar)

`/api/v1/admin/users`: список, один, создать, изменить, удалить.
Код: `schemas/user.schema.ts`, `services/user.service.ts`,
`controllers/user.controller.ts`, `routes/user.routes.ts`.

- **Пароль** хэшируется [bcrypt](https://www.npmjs.com/package/bcryptjs)
  (cost 12) при создании и при смене. В ответах никогда нет
  `password_hash`.
- **Роль приходит словом** (`"student"`), а в таблице `role_id`. Поэтому
  `INSERT ... SELECT r.id ... FROM roles r WHERE r.title = $16`: id роли
  берётся прямо внутри INSERT, одним запросом.
- **Телефон и email уникальны** (UNIQUE в базе). Повтор → код `23505`,
  по имени ограничения (`users_phone_unique` / `users_email_unique`)
  отвечаем **409** и говорим, какое поле занято.
- **Выключить, а не удалить:** `PATCH { "status": false }`.
  Выключенный не может войти (403 при логине). Пользователя с оплатами
  удалить нельзя (409).
- **Защита от самоблокировки:** админ не может выключить, понизить или
  удалить сам себя (400). Иначе он мгновенно теряет доступ, а админов
  может не остаться.
- Фильтры списка: `role`, `search` (имя или телефон), `status`,
  `page`, `limit`. WHERE собирается из массива условий
  (`conditions.join(" AND ")`).

## 5.3 Статистика для дашборда

`GET /api/v1/admin/stats`: числа для карточек. Код:
`services/stats.service.ts`.

- Один SQL с подзапросами `(SELECT COUNT(*) ...)`: одна поездка в базу
  вместо девяти.
- `COALESCE(SUM(amount), 0)`: сумма по нулю строк — это NULL, а нам
  нужен 0.
- Пользователи по ролям: `LEFT JOIN` + `GROUP BY`. LEFT JOIN оставляет
  роли, у которых 0 человек.
- Выручка считается только по `status = 'succeeded'`.
  [date_trunc](https://www.postgresql.org/docs/current/functions-datetime.html#FUNCTIONS-DATETIME-TRUNC)
  `('month', now())` даёт начало текущего месяца.

## 5.4 Содержимое курса: разделы → уроки → материалы

Код: `content.routes.ts`, `section.*`, `lesson.*`, `material.*`.

- **Вложенные URL только для списка и создания:**
  `POST /courses/7/sections` (раздел курса 7), а дальше `/sections/3`.
  Короткие адреса, и id родителя не нужно отправлять дважды.
- **404 для родителя:** раздел в несуществующем курсе отклоняет внешний
  ключ (`23503`), и мы отвечаем «Course not found».
- **Удаление каскадом:** удалишь курс, уйдут его разделы, уроки,
  материалы, файлы (`ON DELETE CASCADE` в схеме).
- **Порядок:** `position` (0, 1, 2...), при равенстве по `id`.
- **Транзакция** (`utils/sql.ts → withTransaction`): материал и его файлы
  сохраняются **вместе или никак**. `BEGIN` → запросы → `COMMIT`, при
  ошибке `ROLLBACK`. Проверено: второй файл упал, первый файл и сам
  материал тоже не сохранились.
  [node-postgres: transactions](https://node-postgres.com/features/transactions)
- **Файлы одним запросом:** `json_agg(...)` собирает файлы материала в
  JSON-массив прямо в SQL, `FILTER` + `COALESCE` дают `[]`, когда файлов
  нет. [Aggregate functions](https://www.postgresql.org/docs/current/functions-aggregate.html)
- Файлы пока ссылки (`file_path`). Настоящая загрузка (S3) будет позже и
  заполнит те же колонки.

## 5.5 Ментор и студент

Три роли, три входа в API:

| Префикс           | Кто     | Что может                                                           |
| ----------------- | ------- | ------------------------------------------------------------------- |
| `/api/v1/admin`   | admin   | всё                                                                 |
| `/api/v1/mentor`  | mentor  | только свои курсы: контент, задания, экзамены, студенты, результаты |
| `/api/v1/student` | student | только курсы, на которые записан: уроки, «пройдено», экзамены       |

**Новая таблица `course_mentors`** (связь «ментор ↔ курс»). Отдельная
таблица, а не колонка `mentor_id` в `courses`: так у курса может быть
один ментор или несколько (связь [многие-ко-многим](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-FK)).
`UNIQUE(course_id, user_id)` не даёт привязать одного ментора дважды.

**Миграция.** В твоей базе уже были данные, а файлы схемы Docker
загружает только в пустую базу. Поэтому изменение лежит отдельным файлом
`docs/database/migrations/001-course-mentors.sql`: он только добавляет
таблицу и ничего не удаляет, его можно запустить повторно. Новые
установки получают ту же таблицу из основных файлов схемы.

**Как ментору запрещается чужое: guard.** Файл
`middleware/course-access.middleware.ts`.

1. Любой объект принадлежит одному курсу: вопрос → экзамен → урок →
   раздел → курс. `services/access.service.ts → courseIdOf` поднимается
   по этой цепочке одним SQL с JOIN.
2. Guard берёт id из URL, находит курс и спрашивает: этот ментор
   привязан к курсу (`course_mentors`)? Этот студент записан на курс
   (`user_courses`), и курс включён? Если нет — **403**.
3. Маршруты контента написаны **один раз** (`createContentRouter`), а
   подключены дважды: у админа с `allowAll`, у ментора с
   `mentorOwnsCourse`. Один код, две панели.

**Студент.**

- **Прогресс** = пройденные уроки / все уроки курса, в процентах. Урок
  отмечается в `lesson_progress`. `ON CONFLICT DO NOTHING`: повторная
  отметка не создаёт дубль и не даёт ошибку.
- **Экзамен оценивает сервер.** Студент получает вопросы **без**
  `correct_answer` и присылает только буквы. Правильные ответы сервер
  берёт из базы и считает баллы сам. Поэтому из браузера нельзя
  прислать «у меня 100%». Без ответа = неправильно. `passed` = процент
  ≥ `pass_percent` экзамена.
- Каждая попытка сохраняется в `exam_attempts`, её видят студент
  (`/student/results`), ментор и админ (`/courses/:id/results`).

**Запись на курс без оплат.** Пока оплат нет, админ сам записывает
студента (`POST /admin/courses/:id/students`) и привязывает ментора
(`.../mentors`). `INSERT ... SELECT ... WHERE r.title = 'student'`
проверяет роль прямо в SQL: ментора нельзя записать студентом.

**Что не сделано и почему.** Проверка домашних заданий: в схеме нет
таблицы для присланных решений (было решено «не в v1»). Задания
(`exercises`) уже есть, а сдача и оценка будут отдельным шагом.

## 7. Docker

### Что это

Docker запускает программы в **контейнерах**. Контейнер — как коробка для
переезда: внутри программа и всё, что ей нужно (нужная версия, библиотеки,
настройки). Коробка одинаково открывается на любом компьютере. Поэтому
пропадает вечная проблема «у меня работает, а у тебя нет».

| Слово             | Простыми словами                                | У нас                              |
| ----------------- | ----------------------------------------------- | ---------------------------------- |
| **Образ** (image) | рецепт, только для чтения                       | `postgres:18`                      |
| **Контейнер**     | запущенная программа, приготовленная по рецепту | `it-live-lms-db`                   |
| **Volume**        | сейф для данных: живёт отдельно от контейнера   | `db-data` (наша база)              |
| **Порт**          | дверь из контейнера наружу                      | `5433` (снаружи) → `5432` (внутри) |
| **Compose**       | один файл описывает все контейнеры проекта      | `docker-compose.yml`               |
| **Docker Hub**    | «магазин» готовых образов                       | оттуда скачан `postgres:18`        |

### Контейнер против виртуальной машины

Виртуальная машина — отдельный дом со своим фундаментом (своя операционная
система целиком): тяжёлая, долго запускается. Контейнер — квартира в общем
доме: фундамент (ядро системы) общий, поэтому контейнер лёгкий и стартует
за секунды.

### Docker на Windows

Docker придумали для Linux: контейнеры используют **ядро Linux**. У Windows
другое ядро, поэтому **Docker Desktop** на Windows тихо запускает маленький
Linux через **WSL 2**. Именно поэтому мы ставили WSL. То есть Docker на
Windows работает, но внутри всё равно Linux. (Бывают и Windows-контейнеры
для программ только под Windows, но нам они не нужны.)

На настоящем сервере (VPS с Linux) Docker работает напрямую, без Docker
Desktop и без WSL.

### Что делает наш `docker-compose.yml`

- берёт образ `postgres:18`;
- называет контейнер `it-live-lms-db`;
- берёт пароль и имя базы из корневого `.env`;
- открывает порт **5433** на твоём компьютере (5432 занят старым Postgres,
  установленным в Windows);
- хранит данные в volume `db-data`, поэтому они переживают перезапуск;
- при **самом первом** запуске (пустой volume) сам выполняет SQL-файлы из
  `docs/database/`, то есть создаёт все 18 таблиц;
- `restart: unless-stopped`: база сама поднимается вместе с Docker
  Desktop.

### Команды (из корня проекта)

| Команда                     | Что делает                                            |
| --------------------------- | ----------------------------------------------------- |
| `docker compose up -d`      | создать и запустить (если ещё нет)                    |
| `docker compose ps`         | статус: запущена ли база                              |
| `docker compose stop`       | остановить (данные сохраняются)                       |
| `docker compose start`      | запустить снова                                       |
| `docker compose logs db`    | логи базы                                             |
| `docker compose down`       | удалить контейнер (данные в volume остаются)          |
| ⚠️ `docker compose down -v` | удалить контейнер **и все данные**. Только осознанно! |

**Главное правило:** Docker Desktop должен быть **запущен**, иначе базы
нет и сервер отвечает 500 / health 503.

### Интерфейс Docker Desktop

Слева меню, по центру список. Названия пунктов зависят от версии, главные
такие:

- **Containers**: запущенные и остановленные контейнеры. Здесь
  `it-live-lms` → `it-live-lms-db`: зелёная точка — работает, кнопки ▶
  (start), ⏹ (stop), 🗑 (delete). Клик по контейнеру открывает вкладки
  **Logs** (то же, что `docker compose logs`), **Inspect** (настройки),
  **Exec** (терминал внутри контейнера), **Stats** (память и процессор).
- **Images**: скачанные образы (`postgres:18`, около 650 МБ).
- **Volumes**: сейфы с данными. Здесь `it-live-lms_db-data`, в нём наша
  база. Удалишь его — удалишь данные.
- **Builds**: сборки собственных образов (понадобится при деплое).
- **Docker Hub / Scout / Extensions / Models / Ask Gordon**: магазин
  образов, проверка уязвимостей, плагины, AI-модели, AI-помощник. Нам пока
  не нужны.
- Внизу: статус **Engine running** (Docker работает), расход памяти и
  процессора. Шестерёнка вверху справа — настройки.

### Что ещё можно делать с Docker

- **Запускать что угодно без установки:** Redis (кеш), MinIO (хранилище
  файлов как Amazon S3, пригодится для материалов курсов), Nginx,
  pgAdmin. Одна строчка в `docker-compose.yml`, и сервис готов. Не нужен —
  удалил, в системе ничего не осталось.
- **Держать разные версии рядом:** Postgres 16 для одного проекта и 18 для
  другого, без конфликтов.
- **Упаковать наш собственный сервер и фронтенд** в образы (через
  `Dockerfile`) и запустить их на VPS одной командой. Это шаг «первый
  деплой».
- **Тесты в CI** (GitHub Actions): тесты запускаются в таком же контейнере,
  как у тебя.
- **Новый разработчик** делает `git clone` + `docker compose up` и через
  минуту у него та же база, что у тебя.

## 8. Как смотреть базу в pgAdmin

У тебя **два** Postgres: порт **5432** — установленный в Windows (не наш),
порт **5433** — наш, в Docker.

1. Открой **pgAdmin 4** из меню «Пуск».
2. Правой кнопкой по **Servers** → **Register → Server…**
3. **General → Name:** `IT Live LMS (Docker)`.
4. **Connection:** Host `localhost`, Port **`5433`**, Maintenance database
   `it_live_lms`, Username `lms`, Password из корневого `.env`
   (`POSTGRES_PASSWORD`). **Save**.

**Забыл пароль?** Их два, не путай:

- **Пароль базы** (пользователь `lms`): открой корневой `.env` проекта
  (`notepad .env` из корня) и возьми значение `POSTGRES_PASSWORD`.
- **Master password pgAdmin** (pgAdmin спрашивает его при запуске, им
  он шифрует сохранённые пароли): если забыл, в этом окне нажми **Reset
  Master Password**. pgAdmin забудет сохранённые пароли серверов, задай
  новый master password и снова введи пароль базы из `.env`.

Таблицы: **IT Live LMS (Docker) → Databases → it_live_lms → Schemas →
public → Tables**. Данные: правой кнопкой по таблице → **View/Edit Data →
All Rows**. Свой SQL: выдели базу → **Tools → Query Tool**.

Без pgAdmin, из терминала:

```bash
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT id, phone, full_name FROM users;"'
```

## 9. Postman

- **Коллекция** «IT Live LMS API»: папки Health, Auth, Errors. Каждый
  запрос с автотестами (вкладка **Scripts → Post-response**).
- **Environment** «IT Live LMS (local)»: `baseUrl`, `adminPhone`,
  `adminPassword`. В запросах они пишутся как `{{adminPhone}}`. Значения
  вводишь сам, в git они не попадают.
- **Run** на коллекции запускает все запросы с тестами по порядку.
- Postman хранит cookie как браузер, поэтому после **Login** запрос **Me**
  работает сам.
- **Главная копия** — файлы в `postman/` в репозитории. Копия в облаке
  Postman (workspace menTalabaman) обновляется после каждого изменения
  файла.

## 11. Показ преподавателю (по шагам)

### Утром, до урока (5 минут)

1. Открой **Docker Desktop** и дождись внизу «Engine running». База
   запустится сама.
2. Открой проект в VS Code и запусти терминал (Ctrl+`):
   ```powershell
   docker compose ps
   ```
   `it-live-lms-db` должен быть **Up**.
3. Запусти сервер:
   ```powershell
   cd server
   npm.cmd run dev
   ```
   Должно появиться «Server is running on http://localhost:4000». Этот

   Если порт занят другим проектом (`it-live-LMS-native`), сначала
   останови его (Ctrl+C в его терминале).
4. Открой в браузере http://localhost:4000/api/health и проверь, что там
   `{"status":"ok","database":"ok"}`.
5. В Postman: **Import** → `postman/it-live-lms.postman_collection.json`

   **IT Live LMS (local)**. Нажми **Run** на коллекции: все тесты должны
   быть зелёные. Если что-то красное, это видно до урока, а не во время.
6. Открой pgAdmin и подключись к серверу на порту **5433** (раздел 8).

### Сам показ (10–15 минут)

**1. Что это и из чего сделано (1 минута).** «LMS для онлайн-школы:
админ создаёт пользователей, курсы, разделы, уроки и материалы. Сервер на
Node.js + Express + TypeScript, база PostgreSQL в Docker, SQL пишу сам
через `pg`, без ORM. Всё проверено тестами в Postman.»
В VS Code покажи папку `server/src` и путь запроса: `routes →
controllers → schemas → services → db` (раздел 3).

**2. База (1 минута).** Docker Desktop → контейнер `it-live-lms-db`.
pgAdmin → `it_live_lms` → Tables: 19 таблиц. Скажи: «Схема лежит в
`docs/database/*.sql`, Docker загружает её при первом запуске».

**3. Все тесты сразу (2 минуты).** Postman → коллекция → **Run** →
**Run IT Live LMS API**. 159 запросов, 288 проверок, все зелёные. Скажи:
«Каждый маршрут проверен: правильные ответы, ошибки 400/401/403/404/409,
пароли нигде не возвращаются. Тесты сами за собой убирают».

**4. По одному запросу (5–7 минут).** Открывай запросы из папки
**Admin** по порядку и нажимай **Send**. Порядок важен: каждый
запоминает id для следующих.

| Запрос                                                                                     | Что сказать                                                            |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| Auth → **Login**                                                                           | Вход по телефону. Токен JWT в httpOnly cookie, JavaScript его не видит |
| Auth → **Me without a cookie → 401**                                                       | Без входа не пускает                                                   |
| Admin → **Login as admin**                                                                 | Снова вход (папка Auth кончается выходом)                              |
| **Dashboard stats**                                                                        | Числа для карточек дашборда, одним SQL-запросом                        |
| Users → **List users**                                                                     | Поиск, фильтр по роли и статусу, пагинация, `total`                    |
| Users → **Create student**                                                                 | Пароль хранится как bcrypt-хэш, в ответе его нет                       |
| Users → **Create user with a taken phone → 409**                                           | Телефон уникален, база не даст дубль                                   |
| Users → **Log in as the student**, затем **Student opens the admin panel → 403**           | Роли работают: студент в админку не попадает                           |
| Users → **Log in as admin again**                                                          | Возвращаемся админом                                                   |
| Categories → **Create category**, Levels → **Create level**, Courses → **Create course**   | Каталог. `slug` делается из названия                                   |
| Courses → **List courses with filters**                                                    | Поиск + фильтры + страницы                                             |
| Course content → **Create section**, **Create lesson**, **Create material with two files** | Дерево курса. Материал и файлы сохраняются одной транзакцией           |
| Courses → **Delete a category that has courses → 409**                                     | База защищает данные (RESTRICT)                                        |

**4б. Три роли (3–4 минуты).** Папка **Mentor and student**, тоже по
порядку, **Send** на каждый:

| Запрос                                                            | Что сказать                                                                                                           |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 1. Setup → всё до **List the course's students**                  | Админ создаёт курс, урок, задание, экзамен с вопросами, ментора и студента, привязывает ментора и записывает студента |
| 1. Setup → **Link a student as mentor → 400**                     | Роль проверяется прямо в SQL                                                                                          |
| 2. Mentor → **My courses**                                        | Ментор видит только свой курс                                                                                         |
| 2. Mentor → **Someone else's course → 403**                       | Чужой курс закрыт (guard)                                                                                             |
| 2. Mentor → **Add a lesson to my section**                        | Ментор сам добавляет контент в свой курс                                                                              |
| 3. Student → **My courses**, **Open the lesson**                  | Курсы с прогрессом; урок с видео, материалами, заданием, экзаменом                                                    |
| 3. Student → **Mark the lesson as done**, **Progress is now 50%** | Прогресс считается сам                                                                                                |
| 3. Student → **Open the exam (no answers)**                       | Правильных ответов студент не видит                                                                                   |
| 3. Student → **Submit: all correct → 100%, passed**               | Баллы считает сервер, не браузер                                                                                      |
| 4. Mentor sees the results → **Results of my course**             | Ментор видит все попытки студента                                                                                     |
| 5. Cleanup → по порядку                                           | Всё тестовое удаляется                                                                                                |

**5. Данные в базе (1 минута).** Пока не запущен Cleanup, тестовые
строки лежат в базе. pgAdmin → таблица `courses` (или `users`,
`materials`) → правой кнопкой **View/Edit Data → All Rows**: это те
самые строки, которые создал Postman.

**6. Уборка.** Отправь запросы из папки **Cleanup** по порядку: тестовые
данные удалятся. Можно показать, что после **Delete section** урок тоже
пропал (каскадное удаление).

**7. Ошибки (если спросят).** Ошибки 500 пишутся в
`server/logs/error.log`: время, адрес и стек, без паролей (раздел 5).
